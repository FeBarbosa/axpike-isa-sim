# SSCAD 2026 Uniform-n Transprecision Experiment Protocol

## Status

This document defines the researcher-approved experiment before the complete
scientific campaign. It is a protocol, not a result report. The experiment must
not begin until the pre-run checklist and reduced-validation gate are complete.

## Research Question

How does uniformly increasing the active-mantissa protection parameter affect
LeNet classification accuracy and the simulated type-selection, quantization,
overflow, underflow, promotion, and result-reduction behavior over the complete
MNIST test set?

The experiment characterizes one workload and one functional numerical model.
It does not estimate hardware area, energy, latency, or performance, and it does
not isolate the causal contribution of an individual floating-point format.

## Independent Variable and Matrix

The only independent variable is the integer `n`, evaluated at every integer
from 0 through 50, inclusive. The same experiment-level value is supplied to
all types. Its effective value is saturated at the maximum supported by each
type:

```text
effective n for a type = minimum of experiment n and the type maximum
```

The generated vector, in canonical order FP64, FP32, FP16, E5M2, is:

```text
minimum(n, 50), minimum(n, 21), minimum(n, 8), 0
```

This definition produces 51 distinct dynamic configurations.

| Experiment interval | Parameters that still change |
| --- | --- |
| n from 0 through 8 | FP64, FP32, and FP16 |
| n from 9 through 21 | FP64 and FP32 |
| n from 22 through 50 | FP64 only |

E5M2 has no configurable protected bit and remains at zero. The prespecified
breakpoints are `n=0`, `n=8`, `n=21`, and `n=50`. They identify changes in the
saturation regime and are replay targets; they are not additional runs.

There are no proportional, per-type, or factorial parameterizations in the
SSCAD experiment. Fixed-format FP16 and E5M2 ADF controls are also outside its
scope.

## Endpoints and Reference Control

The `n=0` endpoint is the combined no-protection dynamic policy. It permits the
most aggressive lower-type selection but does not force all operations to a
single format.

The `n=50` endpoint produces the full-protection vector `50,21,8,0`. It can
still quantize an FP32 or FP64 architectural result to a lower effective type.
It must not be described as original FP32/FP64 execution.

The only reference control is an original FP32/FP64 execution without
transprecision approximation. It will be recovered from repository history and
is not generated by the dynamic matrix. Before it is included in a table or
curve, record and compare:

- parent repository commit and dirty-worktree state;
- relevant submodule commits;
- AxPIKE executable hash;
- LeNet source commit and executable hash;
- build configuration and compiler identity;
- exact command and environment-affecting options;
- hashes of model parameters and all four MNIST IDX inputs;
- instruction-approximation activation and coverage; and
- hashes and schema of the preserved outputs.

If an exact prior artifact cannot be authenticated, rebuild and rerun the
historical revision. If a controlled input or application artifact differs from
the dynamic campaign, do not use the control for a direct numerical difference
without explicitly qualifying the comparison. The planned analysis has 52
points: 51 new dynamic executions and one historical reference.

## Controlled Factors

All 51 dynamic executions must use the same:

- complete 10,000-image MNIST test set and record ordering;
- LeNet weights and normalized inputs;
- RISC-V application executable;
- AxPIKE executable and source revision;
- ADF submodule revision and instruction activation;
- policy name `effective-type-quantization-v4` and version 4;
- application mode `softmax`, followed by argmax and aggregate outcome counts;
- simulator options other than the generated protected-bit vector;
- output schema and extraction scripts; and
- host execution environment as far as it affects reproducibility.

The simulator is expected to be deterministic. Wall-clock performance is not a
scientific response variable, so an ascending run order from `n=0` to `n=50` is
acceptable and simplifies resumability. Each configuration is a separate
process and must write to an isolated output directory.

## Experimental Units and Outputs

The primary application unit is one MNIST test image. Every dynamic
configuration processes the same 10,000 images in the standard test-set order.

The primary response is classification accuracy obtained by applying softmax
to the final logits and then selecting the class by argmax. Softmax is part of
the evaluated network path because this region is used during training and the
experiment must characterize its behavior under the same transprecision
policy. Record:

- correct and incorrect classification counts;
- accuracy as a percentage;
- percentage-point difference from the original reference, when that reference
  has passed the provenance audit.

Image-level and class-level disagreement analyses are outside this article's
scope. The experimental application therefore records aggregate outcomes, not
individual predictions.

The experimental application mode must execute inference, softmax, and argmax,
but must suppress floating-point progress, timing, confusion-matrix, and
evaluation-report calculations. Those auxiliary calculations are not part of
the network and would otherwise contaminate the simulator instrumentation.
The legacy direct-logits mode is diagnostic only and is outside the principal
SSCAD matrix.

The principal simulator responses are:

- effective-type distribution by instruction;
- operand promotions by source and effective type;
- total and value-changing result quantizations from architectural carrier W
  to lower effective type T;
- quantizations that produce signed infinity, underflow, or signed zero;
- total and value-changing result-tag reductions from T to selected lower type
  J; and
- the invalid-result-promotion invariant, which must remain zero.

Record these responses both globally and by stable network region. Region 0 is
unscoped work, region 1 is input normalization, regions 2 and 3 are the first
and second convolution/ReLU/pooling blocks, regions 4 and 5 are FC1 and FC2,
region 6 is softmax, and region 7 is argmax. Reuse the same identifiers for
every image. For every counter key, the global value must equal the sum of all
eight regions.

Regional distributions characterize where effective types and numerical
events were observed under each global `n`. They do not establish an isolated
minimum necessary type for a layer, because values and type metadata propagate
between regions and the same policy is applied throughout the network.

Report raw event totals and normalized rates. Every rate must name its
denominator. Effective-type shares use all supported effective-type instruction
observations. Pair-specific changed-quantization rates use the corresponding
pair-specific quantization total. Pair-specific changed-reduction rates use the
corresponding pair-specific reduction total. Do not combine instruction
observations with register-write counts.

Value-class totals, masked-to-zero totals, lazy recovery, fallback,
unclassified operands, and contextual NaN-boxed FP32 observations are
validation diagnostics. Report them when they explain behavior or threaten an
invariant; do not present them as independent policy outcomes without a stated
research reason.

## Analysis Plan

Plot accuracy and normalized instrumentation responses against integer `n`.
Mark `n=8`, `n=21`, and `n=50` as saturation boundaries. Interpret slopes and
discontinuities within the three regimes separately, because the set of
changing type parameters differs by regime.

The primary analysis is descriptive: the complete fixed MNIST test set is
evaluated rather than sampled. Do not attach a confidence interval that implies
random sampling unless a separate statistical model and its assumptions are
defined. Do not infer image-level or classwise behavior from aggregate counts.

Do not claim that a change after `n=21` is caused by FP64 merely because only
the FP64 protection parameter changes; the workload, propagated metadata, and
prior values remain part of the integrated model. The regime supports a more
focused association, not an isolated hardware causal claim.

Any non-monotonic point is a valid possible scientific result, not
automatically an error. First replay it and inspect invariants, neighboring
points, regional event counters, and effective-type distributions before
interpreting it.

## Validation Gate

### Focused implementation validation

Before application runs, the existing focused simulator tests must pass. This
establishes implementation evidence for quantization, masking, propagation,
special values, metadata, and counter invariants. It does not establish the
application trade-off.

### Reduced integrated validation

All 51 configurations must process the deterministic 62-image MNIST prefix.
That prefix is the smallest contiguous standard test prefix covering every
class, and it is not an accuracy-estimation sample. The previously validated
`n=0` and `n=50` endpoints may be reused only when their executable, application,
fixture, policy, command, and output hashes match the current gate.

A reduced run is valid only if:

- the process exits successfully;
- correct plus incorrect outcomes equal 62;
- all eight stable network regions are present;
- every global transprecision counter equals the sum of its regional values;
- the manifest and CSV identify policy version 4 and the intended vector;
- effective-type totals agree with their per-instruction breakdown;
- every changed counter is a subset of its corresponding total;
- overflow, underflow, and to-zero subsets are internally consistent;
- invalid result promotions equal zero;
- fallback and remaining unclassified operands equal zero; and
- contextual NaN-boxing invariants hold.

NaN, infinity, overflow, or underflow observations are not automatically
failures, but every unexpected occurrence must be explained before proceeding.

### Full scientific evaluation

Only after all 51 reduced runs pass may the same matrix process all 10,000
images. A full run is invalid if it fails the reduced invariants, processes a
count other than 10,000, or cannot be linked to the frozen matrix and artifact
hashes.

## Replay and Anomaly Policy

Replay at least `n=0`, `n=8`, `n=21`, and `n=50` using independent output
directories. Replay any point that is non-monotonic relative to its neighbors,
changes accuracy unexpectedly, produces a new exceptional-value class, or
violates a zero-expected diagnostic.

For deterministic replay, instruction, energy, global and regional
transprecision, and summary outputs must be byte-identical after excluding only fields explicitly
documented as nondeterministic. A mismatch blocks interpretation until its
source is identified.

AxPIKE includes the host process identifier in generated CSV filenames and in
the four application-log lines that announce those filenames. Replay compares
CSV contents by artifact role rather than PID-bearing basename and excludes
only those four announcement lines from the application-log comparison. All
remaining application output must remain byte-identical.

## Per-Run Record

Each run record must contain:

- experiment protocol version and matrix-manifest hash;
- `n`, complete protected-bit vector, configuration identifier, and command;
- start and completion status;
- repository, submodule, application, and executable identities;
- input and model hashes;
- host and compiler information needed to reproduce the build;
- processed-image and outcome counts;
- hashes of raw CSVs, summaries, and logs; and
- extractor version, invariant results, and any anomaly annotation.

The orchestration must be resumable: a configuration is skipped only when its
completion record, expected hashes, and validation status are present. A mere
output directory is not evidence of completion.

## Pre-Run Checklist

- Review and approve this protocol and the paper methodology text.
- Freeze or commit the dynamic-policy implementation and experiment scripts.
- Build AxPIKE and LeNet from recorded revisions.
- Generate schema-3 matrix manifests twice and verify byte identity.
- Pass generator tests and focused simulator tests.
- Implement or adapt resumable runners and extractors for all 51 points.
- Pass the complete 62-image reduced matrix and required replays.
- Recover and audit the original FP32/FP64 reference artifacts.
- Estimate storage and elapsed time on the actual execution host.
- Start the 10,000-image campaign only after recording all identities and
  hashes in a campaign manifest.

## Claim Boundary

Passing the generator tests validates matrix construction. Passing the reduced
matrix validates integrated execution and instrumentation for the reduced
fixture. Only the complete 10,000-image campaign supports statements about the
observed LeNet/MNIST accuracy trade-off. None of these stages validates RTL or
supports area, timing, power, or physical-design claims.
